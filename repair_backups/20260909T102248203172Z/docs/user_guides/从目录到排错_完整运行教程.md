## 2. 输入文件怎么写

当前项目主要有两类输入文件。

第一类是 AMReX/Pele 原生输入文件，常见名字包括：

```text
inputs
inputs.codex_smoke
input.3d
input.2d
input.codex_xxx_smoke
```

第二类是 YAML 工程配置文件，常见名字包括：

```text
input.yaml
input_laminar.yaml
input.codex_yaml_smoke.yaml
```

### 2.1 AMReX/Pele 输入文件基本结构

最小结构通常包含终止条件、几何、网格、AMR、输出和物理模型：

```text
max_step = 100
stop_time = 1.0e-4

geometry.coord_sys = 0
geometry.is_periodic = 0 0 0
geometry.prob_lo = 0.0 0.0 0.0
geometry.prob_hi = 10.0 4.0 4.0

amr.n_cell = 128 48 48
amr.max_level = 1
amr.max_grid_size = 32
amr.plot_int = 10
amr.check_int = 50
```

常用字段：

```text
max_step             最大步数
stop_time            最大物理时间
geometry.prob_lo     计算域下边界
geometry.prob_hi     计算域上边界
geometry.is_periodic 周期边界开关，三维为 x y z
amr.n_cell           基础网格数
amr.max_level        AMR 最大层级
amr.max_grid_size    单个网格块最大尺寸
amr.plot_int         每隔多少步输出 plotfile
amr.check_int        每隔多少步输出 checkpoint
```

PeleC 爆轰常见字段：

```text
pelec.do_hydro = 1
pelec.do_react = 1
pelec.chem_integrator = ReactorRK64
pelec.cfl = 0.4
```

PeleLMeX 工程泄漏/火灾常见字段：

```text
peleLM.do_react = 1
peleLM.chem_integrator = ReactorCvode
peleLM.sdc_iterMax = 2
peleLM.user_defined_ext_sources = 1
peleLM.lo_bc = ...
peleLM.hi_bc = ...
```

泄漏、源项、障碍物、燃料种类通常会在算例自己的 `input.codex_*` 文件中出现。建议改输入文件时按这个顺序改：

```text
1. 先改 max_step、stop_time、plot_int，确认小步数能跑。
2. 再改 geometry.prob_lo/prob_hi 和 amr.n_cell，确认网格尺度合理。
3. 再改泄漏源项、燃料种类、点火时间、障碍物。
4. 最后再开 AMR、更细网格、更长时间和更多并行资源。
```

### 2.2 YAML 输入文件基本结构

YAML 多用于工程前处理、湍流基准和几何配置。典型内容包括：

```yaml
geometry:
  prob_lo: [0.0, 0.0, 0.0]
  prob_hi: [10.0, 4.0, 4.0]

mesh:
  n_cell: [128, 48, 48]
  max_level: 1

physics:
  model: pelelmex
  reacting: true

output:
  plot_int: 10
  check_int: 50
```

实际字段以对应算例脚本为准。工程算例里更推荐先复制已有 `input.codex_*_smoke` 文件再改，不建议从空文件开始写。

## 3. 工程泄漏/火灾怎么跑

工程链路当前优先面向储罐区、管廊、开放区域的可燃气体泄漏、扩散、点火和火焰传播。已验证入口主要集中在 H2，并有 CH4、C3H8、LNG/LPG 气化源项代理能力。

### 3.1 H2 开放区域泄漏扩散 CPU/MPI

用途：确认泄漏源项、开放边界、可燃云团指标和 MPI 稳定性。

```bash

```

常用扩展：

```bash

bash tools/codex_smoke_engineering_h2_leak_open_domain_sensitivity.sh
```

重点看：

```text
是否出现 NaN/Inf
总质量或源项累计是否明显异常
可燃云团体积是否随泄漏和通风合理变化
MPI rank 数变化后结果趋势是否一致
```

### 3.2 H2 管廊障碍物着火 GPU

用途：确认复杂障碍物、泄漏、点火、真实反应、火焰传播和 CUDA 稳定性。

```bash

```

这类算例的通过判断：

```text
泄漏阶段：H2 云团能形成并随流动扩散。
点火阶段：点火窗口内温度、反应速率、主要组分发生可解释变化。
火焰发展阶段：火焰能维持一段时间，不立即熄灭或数值炸掉。
守恒检查：质量、能量、源项累计没有非物理跳变。
数值稳定：无 NaN、无 AMReX abort、无 CUDA illegal memory access。
```

### 5.1 单进程 CPU

一般脚本会自动编译和运行：

```bash

bash tools/codex_smoke_academic_pelec.sh
```

如果手动进入算例目录：

```bash
cd /home/cj/my-pele/examples/academic/detonation_2D

```

可执行文件名字以实际编译结果为准：

```bash

```

### 5.2 多核 CPU MPI

推荐使用脚本变量控制 rank 数：

```bash
cd /home/cj/my-pele
MPI_RANKS=2 bash tools/codex_smoke_engineering_h2_leak_open_domain_mpi.sh
MPI_RANKS=2 bash tools/codex_smoke_academic_pelec_mpi.sh
```

如果手动运行：

```bash

```

MPI 常见注意事项：

```text
rank 数不要大于网格块数太多。
amr.max_grid_size 太大会导致块数少，并行效率差。
先用 2 rank 验证，再逐步升到 4、8、16 rank。
观察日志里的 step/time/dt 是否每个 rank 都正常完成。
```

先确认 GPU：

```bash

```


### 5.4 多 GPU 或 MPI+CUDA

先确认有多卡：

```bash
nvidia-smi -L
```

多卡通常走 MPI，每个 rank 绑定一张卡。当前建议从已有脚本开始：

```bash
bash tools/codex_smoke_academic_pelec_hybrid.sh
bash tools/codex_smoke_engineering_h2_reacting_mpi_cuda.sh
bash tools/codex_smoke_engineering_h2_pipe_rack_reacting_mpi_cuda_restart.sh
```

如果手动指定：

```bash
CUDA_VISIBLE_DEVICES=0,1 mpirun -np 2 ./PeleC*.ex inputs
```

注意：

```text
单卡 GPU 已可作为工程/学术 GPU smoke 的优先入口。
MPI+CUDA 是更严格的组合链路，遇到问题时先拆成 CPU MPI 和单 GPU 两条线分别定位。
多卡性能不只取决于卡数，还取决于网格块划分、通信量和化学反应刚性。
```

## 6. 输出怎么看

### 6.1 先看运行日志

如果脚本直接在终端输出，先看最后 50 行：

```bash
tail -n 50 path/to/run.log
```

常查关键词：

```bash
grep -Ei "nan|inf|abort|error|fail|segmentation|illegal|diverg|cvode|reactor" path/to/run.log
```

正常日志通常会持续出现：

```text
step
time
dt
plotfile 写出
checkpoint 写出
```

### 6.2 看 plotfile

AMReX/Pele plotfile 一般叫：

```text
plt00000
plt00010
plt00100
```

查找：

```bash
find . -maxdepth 3 -type d -name 'plt*' | sort | tail
```

如果有 AMReX 可视化工具，可以用 `amrvis`。如果你用 Python 后处理，建议先用小脚本读取变量列表，再画温度、压力、燃料质量分数、反应速率、速度模。

工程火灾重点看：

```text
温度 T
H2/CH4/C3H8 或对应燃料质量分数
O2
H2O/CO2 等产物
heat release rate 或反应速率相关变量
速度场
障碍物附近回流和火焰锚定区域
```

爆轰重点看：

```text
压力峰值
温度峰值
密度
反应进度或主要组分
波面位置
波速随时间变化
```

### 6.3 看 checkpoint

checkpoint 一般叫：

```text
chk00050
chk00100
```

用途：

```text
长算例中断后重启。
比较重启前后守恒量和波面/火焰位置。
验证 MPI/CUDA restart 链路。
```

如果要减少磁盘压力，可以在确认不需要重启后删除旧 plotfile/checkpoint，但删除前先确认路径：

```bash
pwd
find . -maxdepth 2 -type d \( -name 'plt*' -o -name 'chk*' \) | sort
```

### 6.5 怎么判断一个算例初步跑通

工程泄漏/火灾：

```text
1. 泄漏源项累计质量为正，且没有突跳到非物理数量级。
2. 可燃云团先形成，再随通风/浮力/障碍物扰动扩散。
3. 点火后温度和反应速率出现峰值。
4. 火焰在一段时间内维持传播或稳定燃烧。
5. 全程没有 NaN、Inf、AMReX abort、CUDA device error。
6. CPU MPI 和 GPU smoke 至少各自完成一条代表算例。
```

学术爆轰：

```text
1. 初始扰动后形成反应波或爆轰波。
2. 波面位置随时间推进。
3. 压力、温度、密度峰值趋势合理。
4. 无负密度、负压力、NaN、Inf。
5. CPU、MPI、GPU 入口至少分别完成 smoke。
```

## 7. 常见错误怎么查

### 7.1 找不到输入文件

现象：

```text
Cannot open inputs
Error parsing input file
```

检查：

```bash
pwd
ls -lh
find examples -maxdepth 3 -type f -name 'input*' -o -name 'inputs*'
```

处理：

```text
确认当前目录是否是算例目录。
确认脚本里传入的输入文件名是否存在。
优先复制已有 input.codex_*_smoke 再改。
```

### 7.2 输入参数拼写错误或类型错误

现象：

```text
ParmParse error
Unknown parameter
bad lexical cast
```

检查：

```bash
grep -n "你改过的关键词" examples/engineering/h2_leak_3d/input.codex_xxx
```

处理：

```text
不要猜参数名，先在同类输入文件里搜索。
数值字段不要带中文单位。
数组字段维度要和二维/三维一致。
```

### 7.3 NaN、Inf 或计算发散

现象：

```text
NaN
Inf
Diverged
```

检查：

```bash
grep -RniE "nan|inf|diverg|abort" docs/codex_audit/evidence examples | tail -n 80
```

优先处理：

```text
降低 cfl。
减小 max_step，先跑 10 到 50 步定位。
减小泄漏源项或点火能量。
把点火时间推迟，先让泄漏扩散稳定。
降低 AMR 层级，先在 max_level=0 上验证。
检查压力、温度、质量分数初值是否非物理。
```

### 7.4 反应积分器失败

现象：

```text
CVODE error
Reactor failed
chemistry integration failed
```

处理：

```text
减小时间步或 CFL。
检查点火温度和燃料/O2 配比是否过激。
先用短步数 smoke，确认刚性阶段能跨过去。
GPU 下失败时，先跑 CPU 同输入，再判断是物理刚性还是 CUDA 后端问题。
```

### 7.5 CUDA/GPU 错误

现象：

```text
CUDA error
illegal memory access
unspecified launch failure
no CUDA-capable device
```

检查：

```bash
nvidia-smi
nvidia-smi -L
echo $CUDA_VISIBLE_DEVICES
```

处理：

```text
先确认驱动可见。
先跑单 GPU smoke。
清理旧编译产物后重编 GPU 版本。
MPI+CUDA 失败时先拆成 CPU MPI 和单 GPU 两个问题。
如果重启后 GPU 才恢复，先重新跑最小 CUDA smoke，再跑长算例。
```

### 7.6 MPI 卡住或并行效率差

现象：

```text
mpirun 后长时间没有 step 输出
rank 数增加后反而更慢
```

检查：

```bash
ps -ef | grep -E "Pele|mpirun" | grep -v grep
```

处理：

```text
先用 MPI_RANKS=2。
减小 amr.max_grid_size，让网格块数足够分配。
确认输出目录没有被旧文件或权限卡住。
不要一开始就上最大网格和最多 rank。
```

### 7.7 磁盘空间不足


### 7.8 工作区污染和算例输出清理

长时间测试后，`git status` 里可能同时出现两类东西：

```text
源码、输入文件、脚本、教程文档     这些不能随便删。
plotfile、checkpoint、临时日志      这些通常属于算例输出，可以按清单清理。
```

先生成源码台账：

```bash
python3 tools/write_current_worktree_source_ledger_report.py
bash tools/verify_current_worktree_source_ledger.sh
```

再生成算例输出清理清单：

```bash
python3 tools/write_current_case_output_cleanup_manifest_report.py
bash tools/verify_current_case_output_cleanup_manifest.sh
```

查看报告：

```bash
sed -n '1,260p' docs/codex_audit/evidence/current_worktree_source_ledger_20260803/current_worktree_source_ledger_report.md
sed -n '1,260p' docs/codex_audit/evidence/current_case_output_cleanup_manifest_20260803/current_case_output_cleanup_manifest_report.md
```

这两个报告默认只审计，不删除文件。清理前按这个原则判断：

```text
可以优先清：plt*、chk*、旧 run.log、临时验证目录、明确标记为 generated/case-output 的条目。
不要清：examples 下的 input、源代码、Makefile、tools 下脚本、docs 下报告和教程。

```

如果磁盘空间不足，推荐顺序是：

```text
1. 先删已经确认不再需要的旧 plotfile。
2. 再删旧 checkpoint，只保留最近或关键重启点。
3. 再删临时日志和中间目录。
4. 最后才考虑重新生成大型验证证据。
```

清理后重新确认：

```bash

python3 tools/write_current_worktree_source_ledger_report.py
bash tools/verify_current_worktree_source_ledger.sh
```

### 7.9 报告旧哈希或哈希循环

现象：

```text
sha256 mismatch
evidence hash mismatch
invalid status
guard report contains failures
entrypoint hashes dynamic reports
```

这类错误通常不是 CFD 算例本身失败，而是报告文件之间的依赖顺序不一致。常见例子是某个上游报告刚被重写，下游 release manifest、status CLI 或 state snapshot 还记录着旧哈希。

优先处理：

```bash
cd /home/cj/my-pele
bash tools/run_current_scope_release_refresh.sh
```

这个 wrapper 会重新跑当前范围验证，写入 `docs/codex_audit/evidence/current_scope_last_run_20260807/` 下的时间戳日志，并在日志末尾写入：

```text
[current-scope] PASS current-scope verification chain
CURRENT_SCOPE_RC=0
```

如果只想快速检查报告链路，不想立刻重跑大算例，按这个顺序复验：

```bash
python3 tools/write_current_phase_release_manifest_report.py
bash tools/verify_current_phase_release_manifest.sh
python3 tools/write_current_verification_chain_coverage_report.py
bash tools/verify_current_verification_chain_coverage.sh
python3 tools/write_current_scope_state_snapshot_report.py
bash tools/verify_current_scope_state_snapshot.sh
python3 tools/write_current_status_cli_report.py
bash tools/verify_current_status_cli.sh
python3 tools/write_current_report_hash_cycle_guard_report.py
bash tools/verify_current_report_hash_cycle_guard.sh
bash tools/verify_current_phase_release_manifest.sh
bash tools/verify_current_status_cli.sh
bash tools/verify_current_scope_state_snapshot.sh
```

判断标准：

```text
current_report_hash_cycle_guard 必须 PASS。
entrypoint_forbidden_hash_hit_count 必须为 0。
current_status_cli 和 current_scope_state_snapshot 必须都能单独 VERIFY-PASS。
不要手工修改 *_report.json 里的 sha256 字段；应重跑对应 writer 和 verifier。
```

### 7.10 结果看起来物理不对

排查顺序：

```text
1. 看单位：长度、压力、温度、质量流率是否统一。
2. 看边界：入口、出口、壁面、开放边界是否设错。
3. 看源项：泄漏方向、位置、孔径、质量流量是否合理。
4. 看初值：燃料和空气是否初始化反了。
5. 看点火：点火位置是否在可燃云团内，点火时间是否太早或太晚。
6. 看网格：泄漏口、障碍物边缘、火焰面是否过粗。
7. 看时间步：刚性反应阶段是否 dt 过大。
```

## 8. 推荐工作流

工程场景建议按这个流程推进：

```text
1. h2_leak_3d 小步数冷态泄漏。
2. 开放区域 MPI 泄漏扩散。
3. 加单个圆柱或多立方体障碍物。
4. 加管廊障碍物。
5. 加点火和真实反应。
6. 单 GPU 长一点时间确认火焰维持。
7. CPU MPI 复验。
8. 再尝试 MPI+CUDA 或更大网格。
9. 接入真实 CAD、真实边界条件和外部标定数据。
```

学术场景建议按这个流程推进：

```text
1. detonation_2D CPU smoke。
2. PeleC MPI smoke。
3. PeleC CUDA smoke。
4. AMR 计划验证。
5. 波速、压力峰值、守恒趋势后处理。
6. 再进入 shock_droplet、spray_test、VOF、D2-law。
7. 最后做气液两相爆轰组合验证。
```

每次改输入文件，建议保存一个可追踪副本：

```bash
cp examples/engineering/h2_leak_3d/input.codex_pipe_rack_xxx \
   examples/engineering/h2_leak_3d/input.your_case_YYYYMMDD
```

每次长算例前，建议先跑当前范围健康检查：

```bash
bash tools/verify_master_plan_current_scope.sh
```

如果只是检查用户教程是否齐全：

```bash
python3 tools/write_complete_walkthrough_guide_report.py
```

```text

```
